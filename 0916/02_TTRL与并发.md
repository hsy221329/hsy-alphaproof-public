# TTRL 与并发

TTRL 的并发可以理解为：**许多 Actor 同时搜索目标及其相关变体，成功轨迹汇入共享 Replay，一个集中式 Learner 持续更新专项模型，再将可用参数交给后续搜索复用。** 搜索完成、梯度更新与参数发布有各自的节奏，不需要把所有题组织成“这一轮全部做完，再统一学习”的同步课堂。

本讲以 AlphaProof 论文、已下载核对的官方 Supplementary Data 1 与参数表为依据，不再依赖未经核对的第三方镜像。官方伪代码说明调用关系，但并非可直接运行的生产程序；nanoproof 则用于对照一种真实工程实现，固定到提交 `4f410c6e7a820557501848f954402514201322a5`。具体 Matchmaker 规则见 [[09_Matchmaker_and_nanoproof]]。[论文与 Methods](https://www.nature.com/articles/s41586-025-09833-y) · [官方伪代码附件 ZIP](https://media.springernature.com/original/springer-static/esm/art%3A10.1038%2Fs41586-025-09833-y/MediaObjects/41586_2025_9833_MOESM2_ESM.zip)

## 1. 从相关题池到共享专项模型

记主 RL 通用模型为 $\theta_G$，原目标为 $T$，相关变体集合为 $V_T$。专项代理从 $\theta_G$ 初始化，随后在 $\{T\}\cup V_T$ 上一边搜索、一边学习。specialist 是这套正在适应的证明代理，不是 Actor 结束后另交给的审批模块，也不是每条变体各自训练出来的一个模型。

课程生成发生在题目层：Gemini 提示、程序化变换、候选验证和演化扩展产生局部练习池。791 是提示示例库的规模，至多 15 轮是变体生成的演化次数；它们都不是参数更新的次数。变体语法合法也不保证命题为真，因此后续允许 prove 和 disprove。变体成功主要通过训练经验改善模型；证明一些特殊情形本身不在逻辑上证明一般目标。

公开设计允许多个目标共享题池。若同时适应 $T_A,T_B$，Matchmaker 可以使用：

$$
\mathcal C=\{T_A,T_B\}\cup V_{T_A}\cup V_{T_B}.
$$

这意味着同一轮专项适应可以服务多个目标，而不是强制“一题一套参数”。不同 Actor 共享的是同一个集中学习过程的参数版本与经验池；他们不需要先各自训练一个模型，再把各模型权重合并。

## 2. Matchmaker 决定哪些题同时在搜索

每当 Actor 空闲，Matchmaker 给它一个新的完整尝试：**一道形式命题、prove/disprove 目标、simulation budget**。一轮 simulation 是树搜索中的选择、扩展和回传过程；预算限制此次搜索的迭代数，不等于固定 token 数或固定耗时。因此，题目难度、搜索路线和预算不同，会自然造成各 Actor 的完成时间不同。

官方伪代码对题库中每道题依据历史计算规则权重，再做加权随机抽样，概率为 $p_i=w_i/\sum_jw_j$，并随机指定 prove/disprove。未知或尚未稳定解决的题通常具有高权重，未解题与稳定证明题降权，已成功证伪题权重为零。这里不存在先给所有变体排出一个课程顺序，再严格逐题执行的要求；近期失败增加预算的具体计算由正文描述，官方伪代码的预算函数仍是固定返回 1000 的占位实现。

于是某一时刻可能同时运行：Actor A 证明原目标 $T_A$，B 证明变体 $V_{A,1}$，C 证伪另一条变体 $V_{A,2}$，D 证明 $T_B$ 的相关题。新变体、曾成功但还不稳定的题、低频重试的困难题，都可能处于在途状态。**题池并非所有题同时展开；正在搜索的是当前被分配给有限 Actor 的那些尝试。** 上述安排是说明性例子，公开材料没有规定目标与变体必须占某个固定比例，也没有保证每个目标始终有专用 Actor。

同一道题也可以被多个 Actor 同时抽中。官方伪代码与所核对的 nanoproof 都没有在分配时给该题设置“独占预订”；不同尝试有各自的搜索树和采样过程。这里的并发首先是不同尝试并行，不应直接理解成多个 Actor 共同修改同一棵证明树。

尝试结束后，outcome 返回 Matchmaker 更新该题历史，成功 proof/disproof 的轨迹另外进入 Replay。这两个反馈用途不同：前者改变未来抽题与预算，后者提供梯度训练数据。超时不是反例，也不会变成一条成功证明样本。某个目标被证明后，正文规定停止为它及其关联变体分配**新尝试**；公开正文没有完整说明在途任务取消、共享变体归属或旧 Replay 清除规则。[Methods：Focused RL](https://www.nature.com/articles/s41586-025-09833-y)

## 3. 并发搜索与参数更新如何衔接

### 3.1 官方伪代码：搜索固定快照，学习连续进行

官方 `run_actor()` 在每次新 game 开始前读取 `storage.latest_params()`，随后使用这个 Network 完成该次搜索。成功 game 写入 Replay，所有完成结果交给 Matchmaker。`train_network()` 则从 Replay 抽 batch，更新自己的 Network，并间隔将参数写入 SharedStorage。这些函数直接出现在官方 ZIP 的 `2025-06-13867A-s2/pseudocode.py` 中。

这种分工把并发中的两类问题分开处理。**参数读取的一致性由搜索快照处理**：Actor 正在构建搜索树时，不需要同时读取 Learner 正在改写的参数。**学习成果的共享由 Replay 和参数发布处理**：多个 Actor 的经验汇入同一个 Learner，更新后的参数供之后启动的尝试使用。Actor 生产数据，Learner 执行更新；不是 A 自己更新权重后，再让 B 继承 A 的模型。

尤其要区分 Learner 的“最新训练参数”与 Actor 能读取的“最新发布参数”。Learner 可以已经更新多步，而 SharedStorage 仍保存前一个发布版本。官方伪代码默认 `checkpoint_interval = 1000`，每隔 1000 个训练步调用 `save_params()`，训练结束再保存一次；因此并非每个 optimizer step 都立即切换全体 Actor。这个 1000 是伪代码配置，生产系统实际发布频率以及 TTRL 是否使用相同频率，公开参数表没有完整披露。

### 3.2 一次更新后，在途尝试与新尝试使用什么版本

设当前发布版本为 $\phi_0$。A 用它尝试 $V_1$，B 同时用它尝试 $V_2$；A 先成功，轨迹进入 Replay。Learner 抽取包括这条轨迹在内的 batch，沿训练链得到新参数，但在发布前，新任务仍只能读到 $\phi_0$。发布 $\phi_1$ 后，空闲 Actor 开始下一次尝试时读取 $\phi_1$，B 已开始的搜索则仍可以用 $\phi_0$ 完成。

| 时点 | Actor A | Actor B | Learner / SharedStorage |
|---|---|---|---|
| 初始 | 用 $\phi_0$ 搜 $V_1$ | 用 $\phi_0$ 搜 $V_2$ | 当前发布 $\phi_0$ |
| A 先成功 | 轨迹送入 Replay，可接新任务 | 原搜索继续 | 抽 batch 并更新训练参数 |
| 新参数尚未发布 | 新任务仍读取 $\phi_0$ | 原搜索继续 | Learner 可已更新多步 |
| 发布 $\phi_1$ | 此后启动的尝试读取 $\phi_1$ | 已在途搜索仍用 $\phi_0$ | SharedStorage 更新 |
| B 随后完成 | 各自继续接任务 | 轨迹入 Replay，下一次读取最新发布版本 | 接收旧版本产生的成功经验 |

因此，**“更新后下一轮统一使用新参数”不适合描述官方伪代码的异步时序**：没有全体 Actor 共同开始的下一轮，也没有要求在发布时强制中断所有旧搜索。新尝试读取最新发布快照，长搜索可能跨越多次发布；不同 Actor 暂时使用不同版本是允许的。上表支持的是官方伪代码的调用逻辑，不足以断言生产系统在长搜索中绝不刷新模型或采用完全相同的内存与通信机制。

旧版本成功轨迹仍然可复用，是因为在同一可信 Lean 环境下，已经验证的证明不会因模型更新而失效。Learner 的 policy 目标是从成功轨迹中学习 tactic，value 目标来自该证明的 return；这不是必须由当前策略刚刚产生动作才能使用的即时反馈。不过旧数据的分布可能逐渐偏离当前模型，Replay 窗口与训练混合用于控制这种影响，并不能保证统计分布完全一致或每次更新都提高成功率。

## 4. 积累多少经验才更新：题数、batch 和发布间隔是三个量

AlphaProof 的公开描述是 Learner 持续从缓冲区取训练 batch，而不是“每解决若干道新题才触发一次更新”。一道成功 proof 可以贡献许多 state–tactic–return 样本，不同长度的 proof 贡献量不同；一份旧轨迹还可以进入后续多个 batch。因此成功题数与训练样本数没有固定换算关系。

[Supplementary Table 6](https://media.springernature.com/original/springer-static/esm/art%3A10.1038%2Fs41586-025-09833-y/MediaObjects/41586_2025_9833_MOESM1_ESM.pdf) 给出的 Main RL batch size 为 **4096**，TTRL 对该项未列替换值，沿用 Main RL；TTRL 的 SFT 混合比例为 **25%**，Replay 容量为 **2000 万个 state–tactic 对**，报告训练步数为 **250 万**。其中 TTRL 的 SFT 来源包括 Mathlib 数据与 Main RL 模型样本，不应简单说成 25% 都是人工 Mathlib 轨迹。按混合比例理解，一个 batch 约含 1024 个 SFT 样本、3072 个 Replay 样本；具体装批与舍入方式未披露。

这些数字回答的是 batch 大小、数据配比与容量，**没有给出“首次更新前至少新增多少成功题或多少新样本”的完整启动条件，也没有规定每个 batch 都必须含 3072 个新产生的不同样本**。有了可用 Replay 后，Learner 可以重新抽取历史成功经验继续训练；每次 Actor 成功也不必立刻触发一个独立梯度步。

| 容易混淆的量 | 实际含义 | 能否当成新成功题门槛 |
|---|---|---|
| 成功题数 | 有多少题或尝试找到有效 proof/disproof | 公开设计未给固定触发题数 |
| batch size 4096 | 一次训练 batch 的样本量 | 不能；含混合数据与历史 Replay |
| Replay 容量 2000 万 | 最多保留多少 state–tactic 对 | 不能；不是必须装满才开训 |
| 伪代码发布间隔 1000 步 | 训练参数交给 Actor 的节奏 | 不能；不是训练启动阈值 |

官方伪代码也没有把这些工程条件全部补全：`sample_batch()` 展示取样后更新的流程，但其中 `sample_transition()` 直接读取 `buffer[0]`，没有实现实际随机取样、空缓冲等待与启动预热；`launch_job()` 也是简化占位。另有 `make_config()` 的 batch size 为 2048，不能覆盖论文参数表报告的 4096。应以参数表报告实验设置，以伪代码说明组件关系，而不把伪代码当成完整运行配置。

### nanoproof 对照：有新经验门槛，但更新时暂停共享模型推理

固定版本的 [nanoproof/rl.py](https://github.com/Kripner/nanoproof/blob/4f410c6e7a820557501848f954402514201322a5/nanoproof/rl.py) 给出了另一种具体时序。默认每个外层训练周期等待新增至少 **100 个可用 transitions**，然后将经验加入 Replay，执行 **2 次 optimizer 更新**；每次更新通过梯度累积使用全局 **512 个样本**，SFT 比例默认 10%。100 是此次等待期间新增经验的门槛，512 是训练 batch，2 是更新次数，三者都不是成功题数。两次更新从整个 Replay 与 SFT 取样，可以复用旧样本，所以 100 个新样本足以支持更大的训练 batch；并发返回也可能让新增数量超过 100。[`ProverWorker.collect()` 与 Actor 调用](https://github.com/Kripner/nanoproof/blob/4f410c6e7a820557501848f954402514201322a5/nanoproof/prover.py)

它与官方快照方案还有一个实质差别：Actor 通过共享推理服务请求 tactic，训练前暂停负载分配器与各 rank 的模型推理，等待已开始的推理 batch 完成，再更新模型；各 rank 完成训练后恢复服务。默认梯度累积次数为 $512/(8W)$，其中 $W$ 是 GPU/rank 数，8 是每设备 microbatch 大小。这通过调度 GPU 上的推理与训练，避免在同一个可变模型上同时前向读取和更新参数。

**暂停的是模型推理服务，并不要求每棵在途搜索树先结束。** `BlockingTacticModel.pause()` 保留待处理请求，Actor 可以停在一次 tactic 请求处；更新结束后继续请求新的模型，已有的树节点和旧估值仍留在树中。因此恢复后的新网络调用使用更新参数，但同一次长搜索可能包含更新前后的估值，不是整棵树重新按新版本计算。[推理暂停与恢复源码](https://github.com/Kripner/nanoproof/blob/4f410c6e7a820557501848f954402514201322a5/nanoproof/inference.py)

这个对照说明，并发与更新的协调不只有一种方案：官方伪代码使用独立发布快照，让旧尝试继续完成；nanoproof 在训练时暂停共享模型推理，随后让在途搜索继续。后者是社区实现的资源协调方式，不能倒推为 AlphaProof 原版 TTRL 的生产时序；nanoproof 也没有实现本讲所述完整的目标—variant 专项调度。

## 5. 参数沿一条训练链前进，回滚不是公开默认机制

对一次集中 Learner 运行，参数继承可以写成：

$$
\theta_G\longrightarrow\theta_0\longrightarrow\theta_1\longrightarrow\theta_2\longrightarrow\cdots.
$$

这里下标表示训练更新，发布给 Actor 的快照只是链中被选中的若干版本。**并行的是搜索尝试，链式的是该 Learner 的参数更新。** 每做一道变体并不会自动产生一个独立子模型；多个 Actor 使用不同快照也不是模型版本回滚。另起一次专项运行可以重新从 $\theta_G$ 初始化，那是跨运行的分叉，与一次运行内部的并发不同。

官方 `SharedStorage.latest_params()` 取最大训练步对应的参数，`train_network()` 直接继续更新；其中没有“新版本必须击败旧版本才发布”、自动挑选历史最佳模型或性能下降后回滚的分支。nanoproof 的这条训练调用链同样是继续更新，检查点评测与保存不构成自动回滚门槛。**公开材料支持链式更新，没有证据支持把版本竞争或自动回滚称为原版标准流程。** 生产系统是否另有保护机制，仍不能由这些公开材料排除或补写。

这种机制也不保证能力单调提高。旧 proof 保留后仍是正确证据，累计已解题集合可以增加；当前模型在固定预算下重新搜索的成功率却可能因遗忘、概率分布变化或随机性而波动。Replay、SFT 混合与检查点保存有助于稳定训练和恢复，但不等于每个新版本都更好。

对小规模研究实现，可以明确选择固定快照异步搜索，或在统一更新屏障处暂停推理；如果另加评测后发布、回滚模型和优化器状态的机制，应标成自己的实现方案。理解 AlphaProof TTRL 时，最关键的是分清这条闭环：**Matchmaker 根据历史安排并发尝试，Actor 提供成功经验，Learner 以样本 batch 沿参数链更新，发布机制决定学习成果何时被搜索复用。** 公开资料给出了这个骨架与主要实验参数，首次启动门槛、生产刷新频率和完整回滚策略仍未披露。
