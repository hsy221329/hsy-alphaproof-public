# 实验与实现

前面几篇回答“原版做了什么、公开项目支持什么”。本篇把它们变成可检验的研究方案。**以下模块安排、字段、接受规则与实验顺序均是设计建议，不是声称 AlphaProof 已公开或采用了完全相同的实现。** 背景依据分别见 [原版 Methods](https://www.nature.com/articles/s41586-025-09833-y)、[Nexus Methods](https://arxiv.org/html/2605.22763v2) 与 [nanoproof 固定版本](https://github.com/Kripner/nanoproof/tree/4f410c6e7a820557501848f954402514201322a5)。

## 先确定要证明什么

最小研究主张不应是“我们复现了 AlphaProof”，而应是一个可证伪的句子，例如：**从同一已有 Lean 模型出发，使用目标相关的可验证经验更新参数，在计入课程生成和训练成本后，比等成本冻结搜索解决更多目标题。**

这个句子包含四个不能省略的限定。同一基座排除了初始能力差异；目标相关经验明确了训练对象；实际权重更新区分训练与缓存；全成本比较排除了只算推理、不算教师或优化器的偏差。

也可以先研究更窄的命题：保留旧树的渐进采样是否比覆盖旧树更有效；历史选题是否增加单位计算的有效训练样本；价值引导是否减少完成证明所需 Lean 执行。窄命题更容易定位因果，不必一开始同时引入规划器、教师训练、多专家和复杂异步。

**不要把成功指标只定为训练 loss 下降。** 学习一个重复轨迹可以让 loss 很快下降，却不增加目标题闭合率。也不要只看训练变体成功率：模型可能越来越擅长生成器提供的简单题，而原目标没有进展。

## 最小闭环如何搭建

建议先使用一个已有逐步证明模型、一个可靠 Lean 环境、一个简单搜索器和一个训练进程。value 可以先使用已兼容的模型，也可以先做不依赖学习价值的基线；不要为了名称完整，匆忙接入语义不匹配的 critic。

**题池。** 从一个小批量目标集合开始，为每个目标记录唯一标识与冻结的形式陈述。先用已有形式题、程序化扰动或人工核验的小量相关引理建立课程。课程生成可以离线完成，但预算仍要记录。允许后续自适应增补；增补不能修改原目标以冒充完成。

**搜索。** 每一收集阶段固定一个模型快照。为每道选中的问题设置尝试上限，返回完整证明、正式证伪、预算耗尽或系统错误。状态恢复、最终验证与结果分类要先通过测试，再收集学习数据。

**样本。** 从验证成功的轨迹抽取 state、tactic、return，并保留轨迹归属、依赖、原始 Lean 环境与策略版本。若使用的是整篇证明模型，样本单元与训练目标应相应调整，不能假装其 token 序列自动就是一条 tactic。

**更新。** 累积足够有效的新样本后，进行有限次参数更新，再保存候选检查点。可以采用原版启发的成功轨迹模仿；也可以研究其他 RL 目标，但名称与损失必须如实说明。一次 batch 的大小、每轮梯度步数和新数据量是三个变量，应分别记录。

**目标重试。** 用更新前后相同的搜索协议重新尝试目标题，记录当前模型成功率与累计已解题数。没有目标重试，最多说明完成了某种训练，不能说明测试时适应对目标有帮助。

用接线伪代码概括如下。它省略具体模型和 Lean 接口，因此不是可直接运行的完整复现：

```python
base = load_frozen_base()
model = copy_for_adaptation(base)
replay = ReplayBuffer()
proof_store = VerifiedProofStore()

while budget.remaining():
    snapshot = freeze_snapshot(model)
    jobs = scheduler.select_jobs(budget=budget)
    results = search_with_frozen_snapshot(snapshot, jobs)

    scheduler.record_all_outcomes(results)
    fresh_samples = []
    for result in results:
        if result.has_complete_proof and final_verify(result):
            proof_store.save(result)
            fresh_samples.extend(extract_training_samples(result))

    if not fresh_samples:
        # 改变选题或补充课程，也必须计入预算；不能无限重复等待。
        if not adjust_curriculum_within_budget():
            break
        continue

    replay.add(fresh_samples)
    previous = save_training_state(model)  # 包括优化器状态。
    train_limited_steps(model, replay, anchor_data=mathlib_data)
    candidate = save_training_state(model)
    comparison = evaluate_fixed_protocol(previous, candidate)
    model = accept_or_restore(comparison, previous, candidate)
    retry_original_targets(model, budget=budget)
```

其中 `has_complete_proof` 应按任务的 `objective` 判断：证明任务验证原命题，证伪任务验证其否定，并在提取样本时保留这一语义，不能把反命题证明误记成原命题证明。`accept_or_restore` 是我们增加的保护策略，不是原版已核实的模块；`final_verify` 必须验证原始命题与允许公理，不能只是“编译没有报错”。`budget` 应计入搜索、生成、验证与训练，不能只有循环次数。

## 哪些数据必须记录

一个可审计系统，至少需要三类记录，不宜把它们混在一张“成功/失败”表里。

**尝试记录。** 保存 `target_id`、`problem_id`、问题来源、目标是 prove 还是 disprove、模型检查点、Lean 与 Mathlib 版本、预算、随机种子、起止时间、最终状态与错误类型。这支持回答“这条题是旧模型做的还是新模型做的”“失败是数学困难还是服务异常”。

**可学习轨迹。** 保存当前状态、tactic、下一个状态、分支依赖、回报标签、完整证明引用与最终验证信息。记录搜索树中一条有效边，不等于记录了一条最终成功路线；不能未经说明就把局部合法动作全部作为成功策略监督。

**参数版本。** 保存 `checkpoint_id`、父检查点、训练步数、数据快照或采样日志、优化器状态、发布状态与评估结果。能够画出这条版本链，才适合回答“参数按什么顺序继承”；不能仅从文件名猜先后。

下面是一条建议的尝试元数据示例，值仅为示意，不是实验结果：

```json
{
  "target_id": "target_007",
  "problem_id": "variant_007_012",
  "origin": "generated_variant",
  "objective": "prove",
  "checkpoint_id": "ckpt_0008",
  "search_seed": 17,
  "search_budget_unit": "mcts_simulations",
  "search_budget": 256,
  "outcome": "budget_exhausted",
  "formal_statement_hash": "record_actual_hash_here",
  "environment_revision": "record_exact_lean_and_mathlib_revisions",
  "training_samples_added": 0
}
```

**失败不要压成一种。** `invalid_tactic` 表示动作未被环境接受；`no_progress` 表示没有有效前进；`budget_exhausted` 表示预算内未解；`environment_error` 表示系统故障；`disproved` 才表示存在反命题证明。尤其不能把超时标签当成反例，也不能把本地缓存中的未解状态永久剪掉，因为后续预算、参数或证明环境可能改变。

## 对照实验怎样安排

**第一组，先验证搜索。** 冻结同一模型，对比基础搜索、正确保留旧树的渐进采样，以及可选的学习价值。若研究 nanoproof 修复，应保持候选生成与预算尽量一致，另记录修复前后实际上发生了多少次重复扩展。否则两个版本可能都没走到相关代码，得出“修复没有作用”的结论。

**第二组，验证调度。** 固定模型、题池和总收集预算，对比均匀选择、仅历史权重、历史权重加自适应单题预算。先看单位成本产生的独特成功轨迹与状态覆盖，再进行相同训练预算的更新，观察目标题收益。数据数量增多但信息高度重复，不必然意味着更有效。

**第三组，验证测试时训练。** 使用相同目标题与起始权重，对比冻结模型继续搜索、用不相关但同等数量的成功轨迹训练、用目标相关轨迹训练。这能区分“任何训练都有效”与“目标相关课程确实带来额外适应”。所有训练、生成与验证都计入预算。

**第四组，验证规划与学习互补。** 固定底层模型，做一个二维组合：不用草图且不训练；用草图但不训练；不用高层草图而做课程训练；同时用草图与训练。保持规划模型固定，不把更换规划模型与新增训练一并作为实验变量。这样才能回答你最关心的“子目标与课程选哪个”。

多模块研究常见陷阱是：先使用一个较弱基线，再在新方法中同时换强基座、增加采样数、接入检索与教师，最后把所有收益归因于 TTRL。解决方式不是写更多消融名字，而是保证每个对照只改变自己要解释的因素。

**统计与报告建议。** 至少给出多次随机运行、逐题成功情况和实际成本；在题目难度差异较大时，采用按题配对的比较，不只报告一个总平均。样本很小时，避免把少数题的提升写成稳定通用规律。可以同时报告每题预算固定的指标与全题池自适应分配的指标，两种协议不要混用。

## 防止虚假进步

**累计证明与当前能力分开。** 系统保存过的证明不会因为换模型而消失，因此累计解题数可持续增加；当前检查点在固定预算下的成功率却可能下降。两者都值得报告。若只展示累计曲线，就不能据此论证每一轮参数更新有效。

**单题适应与题组适应分开。** 对每个测试目标都从同一基座重置，是独立单题适应；在整个测试题集上共享已解题的轨迹，是跨题组适应。后者可以是合法研究协议，但必须明确告知，不能把早先测试题获得的知识隐去后宣称每题独立测试。

**变体按原目标分组划分。** 若训练集和评估集中出现同一目标的高度相似变体，可能把记住局部模板误读为一般能力。目标相关适应本来允许使用目标文本，但最终校准、一般化评估和跨目标迁移应有明确边界；不得使用保留的参考证明来暗中生成课程后仍称“无答案自举”。

**保护原命题与可信环境。** 记录原始形式陈述，检查最终证明的类型、依赖和允许公理；确保新增引理都有完整证明，而不是把未解引理变成假设永久带入最终目标。`sorry` 可以是搜索中间产物，但不能是最终成功标准的一部分。[形式验证背景见 A1、X1]

**记录外部教师依赖。** 如果草图与课程持续由强 API 模型生成，最终系统的收益包括这部分在线能力。要证明小模型真正学会了，需要额外冻结并移除在线教师后评估；若还依赖之前生成的课程或缓存，也应说明其来源与构建成本。保存的新参数并不自动证明获得了可跨问题复用的规划能力。

**成本中纳入失败。** 若先在很多目标题上筛选，只对最后成功的几个统计费用，会低估发现可解题的投入。至少区分每次尝试成本、单位成功成本与整批探索成本。Nexus 的成本讨论正说明了这些口径的差异。[X1](https://arxiv.org/html/2605.22763v2)（§5）

## 何时扩大系统

先出现以下信号，再考虑更复杂的异步和多专家：稳定产生新且非重复的成功经验；一轮更新对保留目标有可重现收益；相同预算下确实胜过继续冻结搜索；日志能解释何处耗时；搜索与最终验证没有已知正确性漏洞。

当单个 learner 已经稳定工作，而 actor 经常等待推理或验证服务时，异步可能提升吞吐；当不同目标族的梯度明显相互干扰时，独立专项模型或 adapter 才成为有实验证据的设计方向。LoRA 是 Low-Rank Adaptation，即通过低秩增量参数进行适应的方法，可以用于降低训练负担，但不是 AlphaProof 原文已经披露的必选结构。

增加模型数、角色数与服务数，本身不等于增加学习能力。每增加一层，都应回答：它提供什么新的可验证信息，带来多少额外成本，有没有比简单基线更好的证据。这样才能把“模仿一个复杂系统”转化为“逐步建立可解释、可验证的证明学习系统”。
