# Nexus与课程

你对两条路线的直觉抓住了一个重要差别：**草图路线努力把当前证明组织清楚，课程路线努力让证明模型更适合当前问题。** 但它们既不是同一件事，也不是只能二选一。本篇先核对 Nexus，再建立能用于设计实验的比较框架。

## Nexus实际做了什么

这里讨论的是 2026 年论文 *Advancing Mathematics Research with AI-Driven Formal Proof Search* 的 v2。它区分四种配置：A 是大模型与 Lean 的基础证明代理；B 在 A 上加入 AlphaProof；C 在 A 上加入草图演化与评分；D 同时具备二者。因此 **Nexus 不必使用 AlphaProof；完整配置 D 才是“草图演化加 AlphaProof”的组合。**[论文 §2](https://arxiv.org/html/2605.22763v2)

其关键对象是 proof sketch，即证明草图：已经写出的形式证明结构，以及尚待填补的证明义务。在线大模型修改草图，Lean 提供反馈，子目标工具尝试填补缺口；演化配置还保存候选草图并用大模型评价，指导后续尝试。论文的 prover 使用 Gemini 3.1 Pro，rater 使用 Gemini 3.0 Flash。[X1](https://arxiv.org/html/2605.22763v2)（§2、Appendix A.1）

**你的“没有训练”判断，在需要限定的意义下成立。** Nexus 的该应用流程没有展示新的权重训练；Methods 明确说未采用 AlphaProof TTRL，而使用低计算量树搜索模式。过程中的进步主要保存在草图、工具反馈、已解子目标缓存和候选种群中，不是写入新证明模型参数。[X1](https://arxiv.org/html/2605.22763v2)（Appendix A.1）

这里需要区分三个完全不同的动作：修改 Lean 文件，是修改候选解；把成功引理缓存起来，是保存可复用证明；对参数执行优化器更新，才是改变模型。它们都可能让系统之后更有效，但不能互换名称。本文把前两者称为推理时搜索与外部记忆，把第三者称为参数学习。

你所说“最后没有得到一个新模型，不能脱离大模型使用”也要拆开。完成的 Lean 证明可以单独检查，不必再次请大模型相信它；但继续对新题生成和修改草图，仍需要框架中的生成模型。论文没有展示把这一能力蒸馏进一个可独立运行的小模型的结果。设计上可以换生成模型或蒸馏，但效果必须另测，不能作为原文已实现的功能。

## 草图不是答案

为了看清子目标拆分的真实作用，设原目标为 $T$，候选引理为 $S_1,S_2$。一份真正有意义的形式草图，应当已经给出“有 $S_1,S_2$ 就能推出 $T$”的证明结构；然后剩下的任务是分别证明这两个引理。

在无额外依赖的简化情形，可写成：已经验证 $(S_1\land S_2)\to T$，仍需分别构造 $S_1$ 与 $S_2$ 的证明。若后一个引理依赖前一个，则还要保存具体上下文和依赖顺序，而不应把它们当成完全独立的两个字符串。这些逻辑说明不依赖特定大模型。

**允许 `sorry` 的意义，是暂时声明一个缺口，不是允许最终证明带缺口。** 编译器可以检查草图外围的表达与推导，却不能因此证明占位处的命题是真的。最终必须填完全部证明义务，并防止通过添加不允许的公理、篡改原目标或保留 `sorryAx` 来伪造完成。Nexus 使用 SafeVerify 进行最终完整性与安全性检查，并按精确 Lean 状态缓存子目标。[X1](https://arxiv.org/html/2605.22763v2)（Appendix A.1）

下面是一个逻辑上有效但没有降低难度的草图示意，未在本次任务中运行 Lean：

```lean
example (n : Nat) : n + n = 2 * n := by
  have h : n + n = 2 * n := by
    sorry
  exact h
```

它确实把最终一步变得简单，却把全部原难度移进 `h`。`sorry` 的数量减少、文件变长、末尾出现 `exact h`，都不足以证明求解有进展。Nexus 的失败分析实际报告了类似问题：核心难点被移到几乎重述原目标的辅助引理中；还有候选把并不存在的文献引理当作待补缺口。[X1](https://arxiv.org/html/2605.22763v2)（§3 Failure Analysis）

**推导解释。** 避免这种现象不能只检查字符串不相同。把 $T$ 改写成一个等价表述仍可能保留全部困难；反过来，一个形式上相似的引理有时确实更容易。所以需要同时追踪逻辑依赖和求解难度：前者由形式检查提供保障，后者只能由搜索反馈、模型评价或人工判断近似估计。

一个有用的代价代理是“最困难剩余子目标的估计成本”，而不只是已经填补的小缺口数量。例如拆成九个一眼能证的目标和一个完全重述原题的目标，已经完成九个并不意味着原难题解决了九成。这里与 AlphaProof 的 AND 瓶颈思想存在直观联系，但不能把两者的评分函数直接等同。

## 评分与调度的关系

你的类比可以保留，但应放在正确抽象层：**两者都在稀缺算力下挑选下一步值得尝试的对象。** 相似性止于这个资源分配框架，具体对象、证据和学习作用不同。

AlphaProof matchmaker 选择的是训练命题及预算，主要证据是历史证明、证伪和未解决结果；Nexus rater 比较的是未完成的证明草图，采用大模型对可行性、清晰度与新颖性的判断，再把排名聚合成评分，供候选选择使用。[A1](https://www.nature.com/articles/s41586-025-09833-y)[X1](https://arxiv.org/html/2605.22763v2)（Matchmaker system；§2）

**为什么 Nexus 需要额外的中间评分？** 完整证明只有成功与否的强验证信号，但多数中途草图都没有完成。若全按“是否全部证明”排序，大量候选得分相同，无法指导有限预算。LLM 评分提供了较细的启发式信号，却不因此成为真值判断。一个看起来有洞见的草图，仍可能留下不可证引理。

**为什么 matchmaker 不等于一个简化的 rater？** 它不阅读草图来推断路线是否优美，而是观察哪些题对当前证明能力仍有学习价值。“更容易成功”也不是唯一目标：总挑最容易题可能只能重复制造已掌握样本；总挑最难题又可能没有学习数据。因此，“有时成功、有时失败”与“尚未充分尝试”在调度中占有位置。

可以把共同框架理解为：每个候选对象都有收益估计和不确定性，系统必须在继续利用已知好对象与尝试未知对象之间分配预算。但要比较具体算法，就必须指定收益究竟是**这份草图更可能完成**，还是**这个训练命题更可能使模型进步**。这两种目标甚至可能相互冲突：某条变体非常容易学习，却对最终目标无益；某份草图包含当前最有希望的路线，却短期很难产出训练样本。

因此，在组会上可以说“二者都含有自适应资源分配”，不宜说“LLM rating 与 AlphaProof matchmaker 本质完全一样”。

## 子目标与课程的差别

**子目标首先具有逻辑依赖。** 当所有必需子目标被证明，而且草图的组合结构已验证，原目标随之成立。它强调显式计划与证明构件复用。其失败点是拆错路线、引入不可证引理、循环依赖，或把难度原封不动地转移到最后一个缺口。

**课程首先具有学习关联。** 解决一组目标附近的题，产生可训练经验，进而改变参数，使原目标更容易被搜索解决。这里通常没有“这些训练题都真，所以原题真”的逻辑蕴含；它依赖技能迁移。其失败点是变体无关、过易、过难、重复，或者训练破坏已有能力。

举一个不依赖论文的例子。要证明某个一般不等式，草图路线可能提出“先证明一个凸性引理，再用它推出原式”，并形式验证后半段推导。课程路线则可能让模型练习相同变量结构下的一批特殊情形、标准凸性操作与代数正规化。前者需要找对足够的引理；后者不一定知道最终引理是什么，但需要训练分布能迁移。

**不是草图才会拆目标。** AlphaProof 的 tactic 搜索本身就有 AND–OR 子目标结构，课程生成策略也包含引理与分解类变体。真正值得讨论的是：是否额外配置能提出较大证明片段的高层规划者，以及是否把这些尝试用于参数更新。不能把两类系统说成“一个会分解，一个完全不会分解”。[A1](https://www.nature.com/articles/s41586-025-09833-y)（Prover agent、Variant generation）

**LEAP 提供另一个组织方法。** 它把高层证明依赖保存在 AND–OR DAG 中，共享引理并防止循环；验证草图确实能在辅助引理成立时推出父目标，再递归处理子目标。它还将大模型审阅用作分解质量启发式，而不只判断草图能否编译。[LEAP §2、§5.3](https://arxiv.org/html/2606.03303v2)

对小模型独立能力这一目标，至少有三条不同研究路径：推理时始终保留强规划模型；先用强模型收集分解与成功证明，再离线训练小模型；或者测试时生成局部课程，在线更新小模型。第二条可能减少部署时对教师的依赖，第三条可能增强目标适应，但没有任何一条由概念本身保证更便宜或更强。DeepSeek-Prover-V2 的训练数据构造与 Kimina 的 TTRL 相关说明，分别为这些组合提供了不同参考，见 03。

## 多智能体与成本

多智能体首先描述“有多个可同时执行的工作单元”，不自动意味着 multi-agent reinforcement learning，即多智能体强化学习。多个冻结大模型实例共同修改和评价候选，不存在联合参数优化也可以工作。多个 actor 为一个 learner 采集数据，同样不能直接推断为多个独立专家间的联合奖励训练。

并发的好处是缩短等待、探索不同路线；代价是总 token、重复工作、通信、验证与状态管理。若 $m$ 个代理各运行 $t$ 小时，墙钟可能接近 $t$，但设备或服务总消耗可能接近 $mt$。这是为什么只说“几小时就完成”不足以比较性价比。

**Nexus 是否肯定更便宜？不能这样下结论。** 其论文在部分研究题上发现完整配置更有优势，在另一些题上基础配置更划算。更重要的是，Fig. 3 的 B、D 成本曲线**未计入 AlphaProof 推理费用**，正文另作估计；整体大规模筛选未成功问题的发现成本也不能从只看成功题的曲线中完全读出。[X1](https://arxiv.org/html/2605.22763v2)（Fig. 3、§5 Cost and Variance）

这不否定论文的比较，而是限定它的计费口径。将这些曲线与 AlphaProof 原文按 TPU 天报告的 TTRL 结果直接比较，还同时改变了题目、初始模型、时间版本、训练摊销与服务成本。没有统一实验就不能说“草图路线一般比课程路线省钱”。

更合适的自建成本账包括：规划模型调用、评分模型调用、底层证明模型推理、Lean 验证、课程生成、参数训练、失败重试，以及缓存构建。最终至少同时报告累计成功率对总成本、成功率对墙钟时间两条曲线。若研究目标是获得可复用的小模型，还应报告适应后脱离在线规划器的表现；否则可能只是买到了一个更强外部教师。

## 应该怎样选择

**设计建议。** 不必现在押注一种路线。先保持同一个底层证明模型，比较四种情形：只搜索；加草图、不训练；不加草图、做目标相关训练；草图与训练都使用。每种都计算完整预算。这样得到的是结构分解与参数适应是否互补，而不是两个巨大工程的含混比较。

“更符合人类证明习惯”可以作为产生设计的理由，但不能替代效果验证。最重要的分界是：当前瓶颈究竟是不会提出关键中间命题，还是已经有合适命题却无法执行足够有效的局部证明？前者更适合检验规划者，后者更适合检验底层证明模型、搜索和训练。相关实验的具体安排见 07。
